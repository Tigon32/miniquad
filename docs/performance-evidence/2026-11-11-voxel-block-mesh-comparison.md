## Workload

One real fixed-scene terrain chunk: `SCENE_SEED = 20_261_111`,
`SCENE_CHUNK_DIMS = 8x12x8` (768 voxels), generated by
`miniquad_voxel::terrain::generate_chunk` at world column origin `(0, 0)`
— the same deterministic generator the mixed-mode client and server both
use for the shared scene. Both sides mesh the chunk with **no resident
neighbor chunk** (a `World` containing only this one chunk on the
`miniquad-voxel` side; a 1-voxel air-padded grid on the `block-mesh` side),
so neither mesher benefits from cross-chunk face culling the other has no
way to perform. This keeps the two outputs an apples-to-apples comparison
of `visible_block_faces`-equivalent work, not a comparison of unrelated
culling strategies.

## Timing (native, release profile, `Instant`-based)

200 repetitions per mesher were timed after a 20-iteration warmup for each
side; the `miniquad-voxel` side ran an additional interleaved 200
repetitions after the `block-mesh` pass (400 total `miniquad-voxel`
samples), for the shared-load mitigation described above.

## Interpretation and limits

- On this single-machine, native, release-profile measurement,
  `block-mesh`'s `visible_block_faces` is substantially faster
  (roughly 19x the mean) than `miniquad-voxel`'s own
  `build_chunk_mesh` for this one-chunk, no-neighbor workload. The most
  likely structural reason, read directly from the two implementations
  (not measured separately): `miniquad-voxel`'s `build_chunk_mesh` performs
  a `World::is_solid` lookup (which re-derives a chunk coordinate and does
  a map lookup on every out-of-chunk-bounds neighbor query) per candidate
  face, where `block-mesh` indexes a flat padded array directly. This is
  a plausible explanation, not a proven root cause — no profiler was run
  as part of this measurement.
- **This does not by itself justify replacing `build_chunk_mesh` with
  `block-mesh`** as a core/production dependency: issue #29's contract
  explicitly restricts `block-mesh` to this isolated benchmark crate.
  Any future change to actually adopt (or structurally match)
  `block-mesh`'s performance characteristics in `companions/voxel/`
  itself would be a separate, explicitly-scoped change with its own
  ADR and evidence.
- **No WASM measurement was taken.** This binary is a native `std` CLI
  tool; it was not built for `wasm32-unknown-unknown` and makes no claim
  about WASM-side relative performance. A WASM-side comparison remains
  **NOT RUN**.
- **No GPU time/memory measurement applies here**: this is a pure CPU
  meshing comparison; no GPU resources are created by either side.
- Only one repetition count (200/400) at one chunk size was measured; no
  sweep across chunk sizes or voxel-density ratios was run. Treat the 19x
  figure as a single data point for this exact workload, not a general
  multiplier.
